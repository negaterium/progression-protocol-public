# Skill system contract

The skill matrix contains 38 shared modules. The catalog keeps the Solo
Leveling and D&D language, while the `description`, detail panel and server
action must agree about what a module actually changes.

## Current organization

| Surface | Modules | Meaning |
| --- | ---: | --- |
| Matrix tree | 23 | Modules with coordinates and visible prerequisite links. |
| Reserve archive | 15 | Catalog modules without coordinates; they remain learnable and selectable instead of disappearing. |
| Active | 7 | Modules with a server action, mana cost, duration or cooldown. |
| Passive | 30 | Modules that currently contribute the catalog `stat_bonus` through the normal level and rank scaling. |
| Ultimate | 1 | `Ultimate Awakening`, which currently contributes a flat all-stat imprint per rank. |

The reserve archive is a presentation boundary, not a gameplay lock. Class and
parent requirements still apply, and all eligible non-ultimate modules count
toward the Ultimate gate.

## Display contract

The tree tooltip, reserve archive and detail panel label each module's runtime
contract. **Active Effect** and **Passive Effect** identify registered server
paths; **Stat Imprint** identifies a module whose current behavior is limited to
its level/rank-scaled `stat_bonus`; **Lore Only** is reserved for future entries
with no implemented effect. Catalog descriptions remain visible as flavor and
reference text, while generated summaries and these labels describe the behavior
the current branch actually applies.

Active modules can also carry a permanent `stat_bonus`; the detail panel shows
that imprint separately. Quest duration is measured in Quests, matching the
status-effect processor.

## Passive and ultimate contract

For a normal stat-backed module, each `stat_bonus` point contributes:

```text
floor(stat bonus × character level × (1 + 0.2 × (Rank - 1)))
```

`Ultimate Awakening` instead contributes `stat_bonus × Rank` as a flat value to
every core stat. These are the mechanics currently implemented for the passive
catalog. Twenty-one passives have additional registered runtime effects:

Names such as Bear Form retain their lore, but their descriptions no longer
promise an unimplemented barrier, transformation or damage reduction. They
remain valid stat-imprint modules until their own mechanics are designed and
tested.

The current stat imprint groups are:

- Strength: Domain of the Monarch, Bloodlust, Iron Fist, plus the active Vital Strike and Mutilate imprints.
- Agility: Dagger Mastery, Critical Strike, Quicksilver, Shadow Step, plus the active Sprint and Stealth imprints.
- Intelligence: Deep Work, Mana Shield, Algorithm, Fireball, Coding, System Design, Life Drain, Curse of Agony, Purification, Entangling Roots, Focus, Holy Light, Meditation, plus Domain of the Monarch, Flow State, Shadow Extraction and Dominators Touch imprints.

- Perception: Time Blocking and Sense.

## Upgrade path

Fresh installations receive the reviewed descriptions from
`database/seeds/catalogs.json`. Existing databases keep their current text until
the numbered `database/migrations/002_skill_catalog_truth.sql` migration is
explicitly applied after a backup. The migration changes only shared skill
description fields; it does not alter player allocations or active status effects.

For an existing PostgreSQL deployment, use this sequence from a source checkout
with the database connection variables already present in the process
environment:

```sh
# 1. Create and verify the operator's normal PostgreSQL backup first.
# 2. Preview all pending reviewed upgrades without writing anything.
npm run db:migrate -- --target-database YOUR_DATABASE --env-file .env.local --check
# 3. Review the pending list, then apply the numbered SQL migrations.
npm run db:migrate -- --target-database YOUR_DATABASE --env-file .env.local --confirm
# 4. Restart the app or refresh the Skills page, then run the source verifier.
npm run skills:verify
```

The numbered migration verifies that all 38 shared rows exist, updates them in
one transaction, and never touches player progress. The runner does not read
`.env` files implicitly; provide the same process environment used by the
deployment. If the preview reports missing rows or an unexpected migration
sequence, stop and investigate before using `--confirm`.

Future lore mechanics should be added one module family at a time with a pure
formula, a server-side action path, a detail-panel summary and a regression
test. A description must not advertise a mechanic before that slice exists.
